# ТЗ: AI-native таск-трекер «TaskTracker»

**Версия:** 0.1 (черновик для утверждения)
**Дата:** 2026-07-22
**Процесс разработки:** по [vibe-coding-guidelines](https://github.com/kravtandr/vibe-coding-guidelines) — см. раздел 12.

---

## 1. Цель и обзор

Персональный AI-native таск-трекер, развёрнутый на домашнем сервере:

- единая канбан-доска со всеми задачами; каждая задача принадлежит проекту;
- LLM (Claude API) автоматически категоризирует и оформляет задачи;
- собственный MCP-сервер, через который внешние AI-агенты (Claude Code, Claude Desktop и др.) управляют задачами;
- отдельная страница авторизации, после которой пользователь перенаправляется на доску;
- полноценная работа и на десктопе, и на мобильном браузере.

Основной пользователь — один (владелец сервера). Архитектура не должна мешать в будущем добавить нескольких пользователей, но в MVP многопользовательность не реализуется.

## 2. Термины

| Термин | Значение |
|---|---|
| Проект | Контейнер задач: имя, цвет, описание. |
| Задача | Единица работы, всегда привязана к проекту. |
| Доска | Общая канбан-доска со всеми задачами всех проектов. |
| Колонка | Статус задачи, отображается как колонка доски. |
| Inbox / быстрый ввод | Поле ввода «сырого» текста, из которого LLM формирует оформленную задачу. |
| MCP | Model Context Protocol — стандарт подключения инструментов к AI-агентам. |

## 3. Сценарии использования

1. **Быстрый ввод**: пользователь пишет «починить бэкап на NAS до пятницы» → LLM создаёт задачу с заголовком, описанием, проектом «Homelab», приоритетом и сроком → задача появляется в колонке To Do.
2. **Работа с доской (десктоп)**: перетаскивание карточек между колонками, фильтр по проекту, поиск.
3. **Работа с доской (мобильный)**: просмотр колонок горизонтальным свайпом, смена статуса задачи через меню карточки (без drag-and-drop).
4. **Агент через MCP**: Claude Code в конце сессии вызывает `create_task` («доделать рефакторинг X»), или агент по расписанию делает `list_tasks` и формирует сводку дня.
5. **Вход**: неавторизованный запрос к любому URL → редирект на `/login` → после входа редирект на исходный URL (по умолчанию — доска).

## 4. Функциональные требования

### 4.1 Авторизация

- **FR-1.1** Отдельная страница `/login` (логин + пароль). Все остальные маршруты и API недоступны без сессии (401/редирект).
- **FR-1.2** После успешного входа — редирект на исходно запрошенный URL (`?next=`), по умолчанию на `/board`.
- **FR-1.3** Сессия: HttpOnly + Secure + SameSite=Lax cookie; срок жизни настраивается (по умолчанию 30 дней, «remember me»).
- **FR-1.4** Пароль хранится как хэш (argon2id или bcrypt). Учётная запись создаётся CLI-командой/переменными окружения при первом запуске — регистрации через UI нет.
- **FR-1.5** Rate limiting на `/login` (например, 5 попыток / 5 минут с одного IP), логирование неудачных попыток.
- **FR-1.6** Выход (logout) с инвалидацией сессии.
- **FR-1.7** MCP и программный доступ к API авторизуются отдельными статическими токенами (см. 4.5), не сессионной cookie.

### 4.2 Проекты

- **FR-2.1** CRUD проектов: имя (уникальное), цвет, короткое описание. Описание — часть «автоиндекса проектов»: оно передаётся LLM как контекст категоризации, чтобы даже коряво сформулированная задача попадала в правильный проект.
- **FR-2.2** Архивирование проекта: задачи скрываются с доски, но не удаляются. Удаление проекта возможно только пустого либо с явным подтверждением (задачи удаляются каскадно).
- **FR-2.3** Предустановленный проект «Inbox» — сюда попадают задачи, для которых LLM не смогла уверенно определить проект. Его нельзя удалить.

### 4.3 Задачи

- **FR-3.1** Поля задачи:
  - `title` (обязательное, ≤ 200 символов);
  - `description` — Markdown, включая чек-листы `- [ ]`;
  - `project_id` (обязательное);
  - `status`: `backlog | todo | in_progress | done` (MVP; настраиваемые колонки — вне MVP);
  - `priority`: `low | medium | high | urgent`;
  - `tags`: список строк;
  - `due_date` (опц.);
  - `sort_order` — позиция в колонке;
  - `source`: `manual | ai | mcp` — кто создал;
  - `ai_meta` (JSON): исходный текст пользователя, уверенность категоризации, модель, timestamp;
  - `created_at`, `updated_at`, `completed_at`.
- **FR-3.2** CRUD задач через UI и REST API; смена статуса фиксирует `completed_at` при переходе в `done`.
- **FR-3.3** Полнотекстовый поиск по title/description/tags.

### 4.4 Канбан-доска

- **FR-4.1** Одна общая доска, колонки = статусы. Карточка показывает: title, цвет/имя проекта, приоритет, теги, срок (с подсветкой просроченных), бейдж «AI», если задача создана/оформлена LLM.
- **FR-4.2** Десктоп: drag-and-drop карточек между колонками и внутри колонки (ручной порядок). Оптимистичное обновление UI, откат при ошибке API.
- **FR-4.3** Мобильный (< 768px): колонки — горизонтальный свайп/табы; смена статуса и приоритета — через action-меню карточки. Тап-таргеты ≥ 44px.
- **FR-4.4** Фильтры: по проекту (мультивыбор), тегам, приоритету; текстовый поиск. Фильтры отражаются в URL (шарабельные ссылки).
- **FR-4.5** Колонка Done по умолчанию показывает задачи за последние 14 дней + кнопка «показать все».
- **FR-4.6** Обновления доски: MVP — refetch по фокусу вкладки и после мутаций; live-обновления через SSE/WebSocket (полезно при работе агентов через MCP) — фича M4, не блокирует MVP.

### 4.5 AI-функции (LLM)

- **FR-5.1 Быстрый ввод (Inbox)**: единое поле «сырого» текста (глобальный хоткей `n`, на мобильном — FAB-кнопка). LLM возвращает структурированный черновик задачи: `title`, `description` (оформленный Markdown, при необходимости — чек-лист подзадач), `project` (существующий или новый — см. FR-5.4), `priority`, `tags`, `due_date` (разбор относительных дат: «до пятницы»).
- **FR-5.2** Черновик показывается пользователю на подтверждение (редактируемая форма, «создать» / «создать без правок» одним нажатием). Настройка «автосоздание без подтверждения» — опционально.
- **FR-5.3 Улучшение существующей задачи**: кнопка «✨ оформить» — LLM переписывает title/description, предлагает теги/приоритет; изменения применяются только после подтверждения (diff-превью).
- **FR-5.4 Категоризация (автоиндекс проектов)**: LLM подбирает проект из существующих, опираясь на их имена и описания; если ни один не подходит — предлагает новый проект (короткое имя + описание в одно предложение), и трекер создаёт его автоматически. У выбранного существующего проекта без описания LLM дозаполняет описание; описания, написанные пользователем, LLM не переписывает. При полной неуверенности (разовая задача без темы) — проект «Inbox».
- **FR-5.5** Деградация: при недоступности LLM (нет сети/ключа, ошибка API) быстрый ввод создаёт задачу «как есть» в Inbox с `title` = введённый текст; UI показывает ненавязчивое предупреждение. Ошибки LLM никогда не блокируют базовый CRUD.
- **FR-5.6** Технические требования к интеграции:
  - официальный SDK `anthropic` (Python);
  - модель настраивается через `ANTHROPIC_MODEL`, по умолчанию `claude-opus-4-8`;
  - structured outputs (`client.messages.parse` + Pydantic-схема) — ответ LLM всегда валидируется схемой, невалидный ответ = сценарий деградации FR-5.5;
  - системный промпт стабилен (prompt caching), список проектов/тегов передаётся в user-сообщении;
  - таймаут запроса ≤ 15 с, 1 повтор при 429/5xx (SDK-механизм `max_retries`);
  - ключ API — только в env на сервере, в браузер не попадает никогда.

### 4.6 MCP-сервер

- **FR-6.1** MCP-сервер — часть бэкенда, транспорт Streamable HTTP на эндпоинте `/mcp`, авторизация Bearer-токеном (`MCP_TOKEN`, генерируется на сервере; поддержка нескольких токенов с именами — чтобы отзывать по одному).
- **FR-6.2** Инструменты (все операции идут через тот же сервисный слой, что и REST API):

| Инструмент | Параметры | Действие |
|---|---|---|
| `list_projects` | — | Список проектов (id, имя, число активных задач). |
| `list_tasks` | `project?`, `status?`, `priority?`, `tag?`, `query?`, `limit?` | Поиск/фильтр задач. |
| `get_task` | `task_id` | Полная информация о задаче. |
| `create_task` | `title`, `description?`, `project?`, `priority?`, `tags?`, `due_date?`, `auto_format?` | Создать задачу; при `auto_format=true` или отсутствии проекта прогоняется через тот же LLM-пайплайн, что FR-5.1. |
| `update_task` | `task_id` + изменяемые поля | Обновить задачу. |
| `move_task` | `task_id`, `status` | Сменить статус (перенести между колонками). |
| `complete_task` | `task_id` | Пометить выполненной. |
| `delete_task` | `task_id` | Удалить (мягкое удаление, см. FR-7.4). |
| `daily_summary` | `date?` | Структурированная сводка: сделано/в работе/просрочено. |

- **FR-6.3** Все инструменты возвращают структурированные данные (JSON), описания инструментов включают указание *когда* их вызывать.
- **FR-6.4** Задачи, созданные через MCP, помечаются `source=mcp` и бейджем на доске.

## 5. Нефункциональные требования

- **NFR-1 Адаптивность**: breakpoints ≥1024 (полная доска), 768–1024 (сжатые колонки), <768 (мобильный режим FR-4.3). Тёмная/светлая тема по `prefers-color-scheme`.
- **NFR-2 Производительность**: доска с 500 активными задачами открывается ≤ 1 с на LAN; мутации API ≤ 200 мс (без LLM); LLM-оформление ≤ 10 с с индикатором прогресса.
- **NFR-3 Безопасность**: HTTPS обязателен (reverse proxy); все API за auth; CSRF-защита для cookie-сессий; заголовки CSP/HSTS; секреты только в env/`.env` (в git не попадают).
- **NFR-4 Надёжность данных**: ежедневный автоматический дамп PostgreSQL в локальную папку бэкапов (ротация ≥ 14 дней); мягкое удаление задач (`deleted_at`) с очисткой через 30 дней.
- **NFR-5 Эксплуатация**: весь стек поднимается одной командой `docker compose up -d`; логи в stdout (docker logs); healthcheck-эндпоинт `/healthz`.
- **NFR-6 Стоимость LLM**: обращения к LLM только по явным действиям пользователя/агента (никаких фоновых массовых прогонов в MVP); лог использования токенов.

## 6. Архитектура и стек

Выбор стека — предмет **ADR-0002** (см. раздел 12); ниже — рекомендуемый вариант.

```
[Браузер SPA] ──HTTPS──▶ [Caddy reverse proxy]
                             │  /api/*, /mcp ──▶ [Backend FastAPI]──▶ [PostgreSQL]
                             │  /* (статика) ──▶ [Frontend build]        │
[AI-агент (MCP client)] ─────┘                        └──▶ [Claude API (anthropic SDK)]
```

| Слой | Технология | Обоснование |
|---|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 + Alembic, Pydantic | Единый язык с LLM-пайплайном и MCP SDK; async; строгие схемы. |
| MCP | Официальный `mcp` Python SDK (FastMCP), Streamable HTTP | Монтируется в то же FastAPI-приложение, общий сервисный слой. |
| LLM | `anthropic` SDK, structured outputs | См. FR-5.6. |
| Frontend | React 18 + TypeScript + Vite, dnd-kit (drag-and-drop), TanStack Query, Tailwind CSS | Зрелый DnD, кэш/оптимистичные мутации, быстрая адаптивная вёрстка. |
| БД | PostgreSQL 16 | Полнотекстовый поиск, JSONB для `ai_meta`, надёжные бэкапы. |
| Auth | Серверные сессии (cookie) + argon2id | Просто и безопасно для одного пользователя; JWT не нужен. |
| Reverse proxy | Caddy | Автоматический TLS (Let's Encrypt / internal CA), минимум конфига. |
| Деплой | Docker Compose (caddy, backend, frontend-static, postgres) | Один хост, одна команда. |

## 7. Модель данных

```
users(id, username UNIQUE, password_hash, created_at)
sessions(id, user_id FK, token_hash, expires_at, created_at)
api_tokens(id, name, token_hash, kind ENUM(mcp,api), last_used_at, created_at, revoked_at)
projects(id, name UNIQUE, color, description, is_inbox BOOL, archived_at, created_at)
tasks(id, project_id FK, title, description, status ENUM, priority ENUM,
      due_date, sort_order, source ENUM(manual,ai,mcp), ai_meta JSONB,
      created_at, updated_at, completed_at, deleted_at)
task_tags(task_id FK, tag)  -- + индекс по tag
llm_usage(id, ts, operation, model, input_tokens, output_tokens, ok BOOL)
```

## 8. REST API (основное)

Префикс `/api/v1`, JSON, ошибки в едином формате `{error: {code, message}}`.

```
POST   /auth/login | /auth/logout        GET /auth/me
GET/POST /projects       GET/PATCH/DELETE /projects/{id}
GET/POST /tasks          GET/PATCH/DELETE /tasks/{id}
POST   /tasks/{id}/move        {status, sort_order}
POST   /ai/draft               {text} → черновик задачи (FR-5.1)
POST   /ai/enhance/{task_id}   → предложение улучшений (FR-5.3)
GET    /healthz (без auth)
```

## 9. Деплой на домашнем сервере

- `docker-compose.yml`: `caddy`, `app` (FastAPI + MCP), `postgres`, volume для БД и бэкапов; контейнер бэкапа (`pg_dump` по cron) либо cron хоста.
- Конфигурация — через `.env` (шаблон `.env.example` в репозитории): `DATABASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `SESSION_SECRET`, `MCP_TOKEN`, `APP_DOMAIN`.
- Внешний доступ (**решено, → ADR-0004**): только локальная сеть — порты наружу не пробрасываются, домен не публикуется. Мобильный и MCP-агенты работают из домашней сети. Caddy выпускает TLS через internal CA (self-signed) либо доступ идёт по HTTP внутри доверенной LAN — уточнить в ADR-0004. Расширение до VPN/Tailscale — возможное будущее изменение, ломающее ничего не должно.
- Полный порядок деплоя, обновления и отката фиксируется в `DEPLOYMENT.md` (runbook по шаблону гайдлайнов); деплой не считается завершённым, пока runbook не в статусе `READY`.

## 11. Критерии приёмки (MVP = M0–M4)

1. Неавторизованный доступ к любой странице/API невозможен; вход через `/login` с редиректом на доску.
2. Задача, введённая одной фразой, за ≤ 10 с превращается в оформленную карточку в правильном проекте; при выключенной LLM — создаётся как есть в Inbox.
3. Доска полноценно работает на iPhone/Android-браузере (смена статуса без DnD) и на десктопе (DnD).
4. Claude Code, подключённый к `/mcp` с токеном, может создать, найти, переместить и завершить задачу; изменения видны в UI.
5. `docker compose up -d` на чистом сервере поднимает всё приложение; есть свежий дамп БД в папке бэкапов.
6. Все quality gates (раздел 12) — зелёные в CI.

## 12. Процесс разработки (vibe-coding-guidelines)

Проект ведётся по <https://github.com/kravtandr/vibe-coding-guidelines>:

1. **Bootstrap (M0)**: одноразовое применение гайдлайнов агентом по `AGENTS-GUIDE.md` — read-only аудит → proposal → adoption ADR (`docs/adr/0001-adopt-vibe-coding-guidelines.md`, с provenance: локатор, immutable commit, версия релиза, дата) → артефакты. Установленные файлы принадлежат проекту.
2. **Единый `AGENTS.md`** в корне — единственный источник правил для всех агентов (Claude Code и др.); правила не дублируются.
3. **ADR** (`docs/adr/`) обязательны до реализации: 0001 — adoption; 0002 — выбор стека (раздел 6); 0003 — схема авторизации; 0004 — модель внешнего доступа (VPN vs проброс порта); 0005 — выбор LLM-модели и формат structured outputs; далее — по триггерам из шаблона (новые зависимости-политики, смена фреймворка/БД/протокола, ломающие изменения интерфейсов).
4. **Quality gates** (фиксируются в `AGENTS.md`, команды — точные, неинтерактивные, ненулевой код при ошибке; те же команды в pre-commit и CI):

| Gate | Статус | Команда (проект) |
|---|---|---|
| Setup | REQUIRED | `make setup` (uv sync + npm ci) |
| Lint | REQUIRED | `make lint` (ruff + mypy; eslint + tsc --noEmit) |
| Fast tests | REQUIRED | `make test-fast` (pytest -m "not slow"; vitest) |
| Full tests | REQUIRED | `make test` (pytest + vitest + API-интеграционные на testcontainers) |
| Build | REQUIRED | `make build` (docker compose build + vite build) |
| Verify | REQUIRED | `make verify` = lint → test → build |
| Pre-commit | REQUIRED | lint + fast tests, конфиг в репозитории |
| CI | REQUIRED | GitHub Actions: `make verify` на PR и main, frozen lockfiles |
| Merge protection | BLOCKED до настройки владельцем | required check = CI verify |

5. **Тесты обязательны** для нового/изменённого поведения; багфиксы — с регрессионным тестом, падающим без фикса. LLM-пайплайн тестируется с замоканным Claude API (валидация схем, деградация); MCP-инструменты — интеграционными тестами через сервисный слой.
6. **Деплой**: только по `DEPLOYMENT.md` в статусе `READY`; setup/CI никогда не деплоят.
7. **Статусы и отчёты**: агенты используют словарь статусов гайдлайнов (`COMPLETE / PARTIAL / BLOCKED / NO-OP`, `PASS / FAIL / NOT_RUN`), не называют работу «done» при PARTIAL/BLOCKED, отчитываются точными командами и exit-кодами.

## 13. Вне рамок MVP

Многопользовательность и роли; нативные мобильные приложения; настраиваемые колонки; повторяющиеся задачи; уведомления (push/email/Telegram); интеграции с календарём; массовые AI-операции («разбери весь бэклог»); OAuth для MCP.

## 14. Принятые решения и открытые вопросы

Утверждено владельцем 2026-07-22 (зафиксировать в ADR на этапе M0):

1. **Стек** (→ ADR-0002): FastAPI + React, как в разделе 6.
2. **Внешний доступ** (→ ADR-0004): только локальная сеть, без проброса портов и публичного домена. VPN/Tailscale — возможное будущее расширение.
3. **Модель LLM** (→ ADR-0005): по умолчанию `claude-opus-4-8`; переопределяется через `ANTHROPIC_MODEL`.
4. **Колонки доски**: четыре — `Backlog / To Do / In Progress / Done`.

Открытые вопросы:

1. Язык интерфейса: русский, английский или i18n сразу?
2. TLS внутри LAN: Caddy internal CA (self-signed, придётся доверить сертификат на устройствах) или HTTP в доверенной сети? → уточняется в ADR-0004.
