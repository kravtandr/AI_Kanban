# ADR-0009: Планировщик трат

- **Статус**: accepted (утверждено владельцем 2026-09-06)
- **Дата**: 2026-09-06

## Контекст

Владелец хочет вести в трекере регулярные траты, список желаемых покупок с ценой и
уже купленное — карточками на отдельной вкладке, с редактированием, периодами
`день/месяц/квартал/год` и датой списания. Требования: SPEC.md §4.7 (FR-8.1–8.6),
проработка: `docs/superpowers/specs/2026-09-06-expense-planner-design.md`.

Ограничения кодовой базы:

- схема применяется через `Base.metadata.create_all` (`bootstrap.py:25`); ADR-0008
  установил, что новая таблица Alembic не требует, а изменение существующей — требует
  безусловно;
- `_call_model` в `services/ai.py:113-181` парсит ответ модели жёстко в `TaskDraft`,
  и именно его мокают все LLM-тесты;
- продовая модель — локальная Qwen без structured outputs, JSON вырезается из текста;
- работа затрагивает три триггера AGENTS.md: схема БД, REST API v1, набор
  MCP-инструментов.

## Решение

- **Трата — отдельная сущность `Expense` в новой таблице `expenses`**, со своими
  сервисом, роутером `/api/v1/expenses`, страницей `/expenses` и MCP-инструментами.
  Существующие таблицы, колонки, эндпоинты и инструменты не меняются.
- **Три статуса-колонки `recurring | wanted | bought`** в одной таблице, с инвариантом
  полей по статусу (период и дата списания только у регулярной, дата покупки только у
  купленной). Перетаскивание между колонками разрешено только `wanted ↔ bought`;
  регулярная меняет тип только через форму.
- **Сумма — `Integer` в копейках.** Итоги складываются точно; дроби появляются один раз
  при приведении регулярных трат к месяцу и округляются после суммирования.
- **Одна валюта** настройкой `EXPENSE_CURRENCY` (по умолчанию `RUB`), без
  конвертации.
- **Журнала платежей нет.** Регулярная трата хранит период и опорную дату; следующее
  списание вычисляется чистой функцией `next_charge` на сервере и отдаётся полем.
  Отмена подписки — флаг `active=false`, не удаление.
- **Единственная правка LLM-слоя — keyword-only параметр `schema` с умолчанием
  `TaskDraft`** у `_call_model` / `_call_anthropic` / `_call_openai`. Черновик траты —
  плоская схема `ExpenseDraft` и отдельный короткий промпт; сервер детерминированно
  доводит черновик до инварианта.
- **REST v1 и MCP расширяются строго аддитивно**: новый роутер, новый
  `POST /ai/draft-expense`, четыре новых инструмента `list_expenses`,
  `create_expense`, `update_expense`, `expenses_summary`. Инструмента удаления нет.
  `source=mcp` ставится сервером.

## Альтернативы

- **Подвид задачи: `tasks.kind` + JSON с ценой и периодом.** Отклонено: требует
  колонок в существующей таблице (Alembic), журнал состояний учёта времени начал бы
  писаться на траты, колонки `TaskStatus` не совпадают с колонками трат, фильтры доски
  и промпт задач пришлось бы учить прятать траты.
- **Две таблицы: регулярные и покупки.** Отклонено: два CRUD, две формы, восемь
  инструментов ради одной вкладки одного пользователя; DnD `wanted → bought` и так
  происходит внутри одной таблицы.
- **Колонки по горизонту времени или по статусу оплаты каждого списания.** Отклонены
  владельцем: второй вариант требует журнала платежей и порождает карточку на каждое
  списание.
- **Сумма как `Numeric(12,2)` или `Float`.** Отклонено: целые копейки не дают ошибок
  округления в итогах и не требуют `Decimal` на границе JSON.
- **Отдельный LLM-слой для трат.** Отклонено: параметр `schema` с умолчанием сохраняет
  все существующие вызовы и моки нетронутыми.

## Последствия

- `create_all` на старте создаст таблицу `expenses` и два новых PG-энума
  (`expensestatus`, `expenseperiod`); шаг миграции в DEPLOYMENT.md не нужен. Правило
  ADR-0008 сохраняется: первая колонка в существующей таблице приносит Alembic.
- Существующий энум `tasksource` переиспользуется для `expenses.source` — значение
  «кто создал» одно на обе сущности.
- Ежедневная чистка `_purge_deleted_tasks_once` получает второй вызов —
  `purge_deleted_expenses`; дочерних таблиц у трат нет, каскады не нужны.
- Статистика фактических трат невозможна: без журнала платежей есть только план.
  Если владелец захочет графики по месяцам, потребуется отдельный ADR с журналом.
- Приведение к месяцу — оценка по среднему календарному месяцу, а не точный расчёт по
  датам; сумма «в месяц» для дневных трат колеблется относительно факта на ±3%.
- Фронтенд получает вторую страницу-доску без общего каркаса с `BoardPage`;
  дублирование DnD-обвязки принято сознательно ради сохранности доски задач.
