# Ручное переназначение проекта и починка автоиндекса (FR-2.1 / FR-5.4)

- **Дата**: 2026-07-26
- **Статус**: design approved (владелец, 2026-07-26)
- **Затрагивает**: FR-2.1, FR-4.1, FR-5.4; ADR-0005 (дополнение)

## 1. Задача

Владелец сообщил три вещи:

1. Хочу менять проект у задачи через правую кнопку (десктоп) и долгое нажатие (мобильный).
2. Хочу «плюсик», которым можно создать проект, если его ещё нет.
3. AI положил обе мои задачи в Inbox, хотя одна явно про проект «Сварог», а вторая — про
   проект в разработке, у которого пока нет названия. Агент должен сам решать: создать
   новый проект или приписать к существующему, опираясь на индекс проектов с описаниями.

## 2. Что уже существует (проверено по коду)

- **Смена проекта у задачи работает**: `PATCH /tasks/{id}` принимает `project_id`
  (`backend/app/api/tasks.py:54`), а `TaskForm` уже содержит `<select>` с проектами
  (`frontend/src/components/TaskForm.tsx:76`), доступный по клику на карточку.
  Пункт 1 — это **ускоритель** доступа к существующей возможности, а не новая функция.
- **CRUD проектов на бэкенде полон**: `GET/POST/PATCH/DELETE /projects`
  (`backend/app/api/projects.py`). В UI нет ни одного места создания проекта — сейчас
  проекты появляются только автоматически из `resolve_project_id`.
- **Механика FR-5.4 реализована целиком**: индекс проектов передаётся в промпт
  (`_project_context`), LLM может предложить новый проект, `resolve_project_id` его
  создаёт, дозаполняет пустое описание и защищает описание Inbox
  (`backend/app/services/ai.py:254`).
- **Регистр имён покрыт**: `find_project_by_name` и `create_project` сравнивают через
  `func.lower` (`backend/app/services/projects.py:101`). «Сварог» и «сварог» не
  расплодятся; «Сварог» и «Svarog» — разные проекты.

Вывод: пункт 3 — не отсутствующая функциональность, а дефект существующей.

## 3. Корневая причина пункта 3

`_project_context` перечисляет **все** проекты, включая Inbox, то есть отдаёт модели
Inbox как полноправный вариант выбора. В базе владельца других проектов не было, поэтому
список выглядел как «выбери из одного варианта» — и слабая локальная модель выбирала.
Диагноз подтверждён замерами (раздел 4), а не рассуждением.

Побочно обнаружен второй дефект: на существующем проекте модель в 2 из 5 прогонов
возвращала имя проекта вместе с описанием
(`'Сварог — Платформа Сварог: бэкенд, UI и деплой.'`), что создало бы проект-мусор с
именем длиной до 100 символов.

## 4. Замеры

Стенд: `qwen36-35b-a3b-no-think` через локальный LiteLLM владельца, по 5 прогонов на
каждую комбинацию (вариант × доска × заметка). Процедура воспроизведения — раздел 8.3.

### 4.1 Пустая доска (реальная ситуация владельца)

| заметка | baseline | вариант A |
|---|---|---|
| «Сделать UI в свароге» | `Inbox` ×5 | `Сварог` ×5 |
| «Оформить инструментарий проверки безопасности…» | `Inbox` ×5 | новый проект ×5 |
| «купить молоко» (разовое) | `Inbox` ×5 | `null` ×5 → Inbox |

Главный риск варианта A — что модель начнёт плодить проекты из разовых поручений —
опровергнут: разовая заметка даёт `null` пять из пяти.

### 4.2 Стабильность имени нового проекта

| вариант | результат за 5 прогонов |
|---|---|
| A, `temperature` не задан (как в проде сейчас) | 3–4 разных имени |
| A, `temperature=0` | `Security Audit Toolkit` ×5 — стабильно, но не на языке заметки |
| **A2, `temperature=0`** | `Инструментарий проверки безопасности` ×5 — стабильно и на языке заметки |

### 4.3 Дыра, которая не закрылась

При существующем «Сварог» заметка «Оформить инструментарий проверки безопасности
приложения в репозитории» уходит в `Сварог` ×5 — в baseline, в A и в A2, включая правило,
прямо требующее проверять скоуп проекта.

Заключение: это не дефект промпта. В самой заметке нет ни одного признака, что речь о
другом проекте (владелец подтвердил: у того проекта ещё нет названия). Второй вызов LLM
(рассматривался как вариант B) той же моделью решал бы ту же недоопределённую задачу,
поэтому в дизайн не входит.

### 4.4 Самоисправление индекса

Индекс: «Сварог» + «Инструментарий безопасности — статический анализ и проверки
безопасности кода в репозиториях и CI».

| заметка | результат (A2, `temperature=0`) |
|---|---|
| та же заметка про безопасность | `Инструментарий безопасности` ×5 |
| новая заметка «прикрутить сканер секретов в CI» | `Инструментарий безопасности` ×5 |
| «Сделать UI в свароге» | `Сварог` ×5 |
| «записаться к стоматологу» | `null` ×5 |

Один ручной перенос задачи наполняет индекс, после чего маршрутизация точна — включая
заметки, которых в стенде раньше не было. Это и есть замысел FR-2.1, и именно он делает
ограничение из 4.3 приемлемым.

## 5. Дизайн: бэкенд

Все правки — в `backend/app/services/ai.py`. Новых сущностей, зависимостей и полей БД нет.

### 5.1 Inbox исчезает из списка выбора

`_project_context` пропускает проект с `is_inbox=True`. При отсутствии других проектов
блок выглядит как `Projects:\n(none yet)`. Inbox остаётся fallback-ом: «нет темы»
выражается через `project=null`, который `resolve_project_id` уже маппит в Inbox без
изменений.

### 5.2 Правило Project в системном промпте — версия A2

Заменяет текущий абзац `- Project:` и требует:

- маршрутизировать в существующий проект, только если заметка **явно** попадает в его
  описанный скоуп; общая технология или расплывчатое тематическое пересечение — не
  основание;
- копировать **только имя** проекта, никогда описание;
- переиспользовать точное имя существующего проекта, если заметка говорит о том же на
  другом языке или в транслитерации («Svarog» → существующий «Сварог»);
- если ни один проект явно не покрывает заметку — обязательно предложить новый, назвав
  его по продукту, системе или домену, а не по самой задаче; 1–3 слова на языке заметки;
- никогда не отвечать `Inbox`, `Разное`, `Misc` и подобными catch-all именами;
- `null` — только для разового поручения без темы.

Промпт остаётся статичным (важно для prompt caching по ADR-0005): список проектов
по-прежнему живёт в user-сообщении.

### 5.3 `temperature=0`

`_openai_chat` начинает передавать `temperature: 0`. Сейчас параметр не задаётся вообще
(`backend/app/services/ai.py:136`) — отсюда недетерминированность из 4.2. Для
anthropic-пути `messages.parse` вызывается без `temperature`; менять его не требуется,
так как замеренная нестабильность относится к self-hosted провайдеру, а трогать
работающий путь без данных не нужно.

## 6. Дизайн: фронтенд

### 6.1 Триггеры меню

Единственный обработчик `onContextMenu` на карточке покрывает правый клик, долгое
нажатие (Chromium и Safari генерируют `contextmenu` по long-press) и клавиатуру
(браузеры генерируют то же событие на клавишу Menu и Shift+F10). Обработчик вызывает
`preventDefault()`.

Конфликта с drag-n-drop нет: `PointerSensor` настроен на `activationConstraint:
{ distance: 8 }` (`frontend/src/pages/BoardPage.tsx:81`), то есть drag начинается от
смещения, а не от удержания. Сдвиг пальца — перетаскивание, удержание на месте — меню.

На карточку добавляются `-webkit-touch-callout: none` и `user-select: none`, чтобы не
всплывала нативная выноска выделения.

Если приёмочная проверка (раздел 8.2) обнаружит браузер, не присылающий `contextmenu` по
удержанию, добавляется fallback: таймер 500 мс на `pointerdown`, отменяемый по
`pointermove` за пределы 8 px и по `pointerup`. Начальная реализация его не содержит.

### 6.2 Компоненты

| Файл | Изменение |
|---|---|
| `frontend/src/components/TaskContextMenu.tsx` | новый: список проектов + пункт «+ Новый проект…» |
| `frontend/src/components/NewProjectModal.tsx` | новый: одно поле «Имя», кнопки «Создать» / «Отмена» |
| `frontend/src/components/TaskCard.tsx` | `onContextMenu`, CSS-подавление нативной выноски |
| `frontend/src/pages/BoardPage.tsx` | состояние меню (задача + координаты), мутации |

Позиционирование: на ширине ≥ `sm` — поповер у курсора с зажимом по границам вьюпорта;
ниже — bottom sheet, потому что привязка к курсору на 390 px бессмысленна. Один
компонент, разное позиционирование через CSS-брейкпоинт.

### 6.3 Поток данных

- Выбор проекта → `PATCH /tasks/{id}` с `{project_id}` → инвалидация `["tasks"]`.
- «+ Новый проект…» → `POST /projects` с `{name}` → на 201 сразу `PATCH /tasks/{id}` на
  новый `project_id` → инвалидация `["projects"]` и `["tasks"]`.

Описание при создании не отправляется: остаётся пустым и дозаполняется AI при первой
смаршрутизированной задаче (`resolve_project_id`, ветка backfill). Это решение владельца
— форма спрашивает только имя.

## 7. Обработка ошибок

- **`POST /projects` → 409** (`{code:"conflict"}`, `backend/app/api/projects.py:23`).
  Ошибка пользователю не показывается: список проектов перезапрашивается, и если имя
  находится без учёта регистра — существующий проект выбирается молча, что и было
  намерением пользователя. Если имя не нашлось, значит совпадение произошло с
  **архивным** проектом (`create_project` проверяет уникальность без фильтра по
  `archived_at`, а `GET /projects` архивные не отдаёт) — тогда показывается сообщение
  именно про архив, а не «уже существует».
- **`PATCH /tasks/{id}` не удался** — тост с ошибкой, состояние доски не меняется.
- **LLM недоступна** — поведение FR-5.5 сохраняется без изменений: `_fallback_draft`,
  задача в Inbox, `ai_ok=false`, CRUD не блокируется.

## 8. Тестирование

### 8.1 Автотесты (входят в `make verify`)

Бэкенд (pytest, сеть не используется, `_call_model` мокается — как требует ADR-0005):

- `_project_context` не содержит Inbox; на доске без других проектов даёт `(none yet)`;
- `resolve_project_id(None)` → Inbox;
- `resolve_project_id` с именем, содержащим описание после тире, не создаёт проект с
  таким именем — регрессия на дефект из раздела 3;
- `_openai_chat` отправляет `temperature: 0`.

Фронтенд (vitest):

- меню рендерит проекты, `aria-checked` стоит на текущем;
- выбор проекта вызывает `PATCH` с ожидаемым `project_id`;
- «+ Новый проект…» вызывает `POST /projects`, затем `PATCH` задачи;
- ответ 409 приводит к выбору существующего проекта без сообщения об ошибке.

Оснастка под эти тесты добавляется в рамках работы: до неё `vitest` был настроен
только на `environment: "node"` и `src/**/*.test.ts`, компонентных тестов в
проекте не было. Добавляются devDependencies `jsdom`, `@testing-library/react`,
`@testing-library/user-event`, `@testing-library/jest-dom` и разделение по
расширению: `.test.ts` — node, `.test.tsx` — jsdom.

Отдельно исправлено окружение тестов бэкенда: встроенный `lower()` в SQLite
работает только с ASCII, из-за чего регистронезависимый поиск проектов не
находил ни одно кириллическое имя — то есть ветка «нашёл существующий проект»
проверялась только на латинице, хотя в проде на PostgreSQL всё работало.
В `conftest.py` для тестового движка регистрируется Python-овский `lower()`.

### 8.2 Приёмочная проверка в реальном браузере

Драйвер на `puppeteer-core` + системный Chrome (`/opt/google/chrome/chrome`):

- десктопный вьюпорт: правый клик по карточке открывает меню; выбор другого проекта
  меняет бейдж проекта на карточке;
- touch-эмуляция 390×844: удержание карточки открывает меню и **не** начинает
  перетаскивание; сдвиг пальца начинает перетаскивание и **не** открывает меню;
- скриншоты обоих состояний прикладываются к отчёту.

### 8.3 Проверка маршрутизации на живой модели

Скрипты стенда из раздела 4 сохраняются как воспроизводимая процедура. В CI они не
входят: требуют доступа к LiteLLM владельца, а ADR-0005 запрещает сеть в тестах.

## 9. A11y

`role="menu"` на контейнере; проекты — `role="menuitemradio"` с `aria-checked` на
текущем; «+ Новый проект…» — `role="menuitem"`. Escape закрывает меню и возвращает фокус
на карточку; стрелки навигируют по пунктам; фокус заперт внутри меню, пока оно открыто.
Соответствует уже проведённому в проекте аудиту по Web Interface Guidelines.

## 10. Границы скоупа

Не входит в эту работу: страница управления проектами; переименование, архивирование и
удаление проектов из UI; «+» внутри `<select>` в форме задачи; уборка
проектов-сирот, создаваемых `/ai/draft` до подтверждения черновика; нечёткое или
транслитерационное сопоставление имён на стороне БД.

**Проекты-сироты** заслуживают отдельного упоминания: `/ai/draft` создаёт проект до
подтверждения (`backend/app/api/ai.py:19`), поэтому отклонённый черновик оставляет
пустой проект. Дефект существовал до этой работы, но с автономным созданием проектов
станет заметнее. Владелец решил не трогать его сейчас: контекстное меню как раз даёт
увидеть такой проект. Выносится в отдельную задачу.

## 11. ADR

Новый ADR не требуется: нет новой зависимости, задающей политику, смены фреймворка, БД
или протокола, ломающих изменений REST API v1, набора MCP-инструментов или схемы БД —
то есть ни одного из условий, перечисленных в `AGENTS.md`.

**Требуется дополнение к ADR-0005.** Он фиксирует «текущая конфигурация владельца:
qwen36-35b-a3b-think на собственном сервере, таймаут поднят до 90 с». Фактическая
конфигурация другая и противоречит записанной: `qwen36-35b-a3b-no-think` с таймаутом
15 с. Основание — замер: think-вариант расходует весь бюджет токенов на рассуждения и
возвращает **пустой** `content`, тогда как no-think отвечает валидным JSON за ~0.5 с.
Дополнение к ADR-0005 фиксирует: модель `no-think`, таймаут 15 с, `temperature=0` для
провайдера `openai` и причину каждого из трёх решений.

## 12. Риски и известные ограничения

| Риск | Оценка | Что делаем |
|---|---|---|
| Заметка без признаков отдельного проекта уходит в похожий существующий | Подтверждён замером (4.3), промптом не лечится | Принимаем. Лечится ручным переносом, после которого индекс самоисправляется (4.4) |
| «Сварог» и «Svarog» как два проекта | Реален: владелец пишет название и так, и так | Строка в промпте про переиспользование имени при транслитерации (5.2). Нечёткое сопоставление в БД сознательно не делаем — легко склеит непохожее |
| `temperature=0` делает повторный черновик той же заметки полностью одинаковым | Не риск, а цель | — |
| Долгое нажатие конфликтует с drag-n-drop | Снят анализом кода: активация по расстоянию, не по задержке | Проверяется приёмочно (8.2) |
