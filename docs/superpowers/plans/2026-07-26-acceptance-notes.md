### Оговорка про метод

Эмуляция не генерирует `contextmenu` по долгому нажатию, а `touchStart` +
`touchEnd` — это тап, дающий `click` при любой длительности удержания. Поэтому
жест меню проверяется прямой отправкой `contextmenu` на карточку без
предшествующего тапа: только так последовательность соответствует реальному
устройству, где браузер шлёт `contextmenu` и **гасит** последующий `click`.

Первая версия драйвера этого не учитывала, и на скриншоте меню оказалось
поверх открытой модалки задачи. Это был артефакт драйвера, но он выявил
незакрытый риск: если какой-то браузер пришлёт и `contextmenu`, и `click`,
пользователь получит модалку под меню. Поэтому в `TaskCard` добавлено гашение
`click` в течение 500 мс после `contextmenu` (метка времени, а не флаг: зависший
флаг съел бы следующий честный клик) и тест на это.

## 4. Найдено попутно, за рамками работы

**Перетаскивание карточек пальцем не активируется.** В эмуляции
`touchStart` + `touchMove` не запускает drag ни до, ни после наших правок.
Причина не в этой работе: `touch-action: manipulation` стоит и на карточке
(`TaskCard`, коммит `07e8d56`, до начала работы), и глобально в
`styles.css:58`, а `PointerSensor` из dnd-kit требует `touch-action: none`,
иначе браузер оставляет жест прокрутке и отменяет поток pointer-событий.

Проверено, что это не регрессия: диф `TaskCard` по этой строке добавляет только
`[-webkit-touch-callout:none]`.

Возможно, на реальном устройстве поведение иное — эмуляция не доказательство.
Но `MobileDropZone` в `BoardPage` существует именно для перетаскивания на
мобильном, и если drag не стартует, эти зоны никогда не появляются. Стоит
проверить на телефоне и, если подтвердится, вынести в отдельную задачу.

# Дополнение 2026-07-27: два дефекта, найденные владельцем на iPhone

Эмуляция обоих не поймала. Оба относятся к iOS-специфике, которую headless
Chrome с `isMobile: true` не воспроизводит.

## 7. Долгое нажатие на iPhone не открывало меню

**Причина.** Утверждение спеки «Safari шлёт `contextmenu` по long-press» верно
только для macOS. iOS Safari этого события по долгому нажатию **не шлёт**, а
добавленный нами `-webkit-touch-callout: none` убирает и системную выноску —
жест не давал вообще ничего.

**Почему приёмка это пропустила.** Эмуляция не генерирует `contextmenu` по
удержанию ни для одного браузера, поэтому драйвер отправлял событие напрямую
через `dispatchEvent`. Такая проверка подтверждает обработчик, но не жест.

**Исправление.** Реализован fallback, который спека описывала как условный:
таймер 500 мс на `pointerdown` с `pointerType !== "mouse"`, отменяемый по
`pointermove` дальше 8 px, по `pointerup` и `pointercancel`. Порог сдвига
совпадает с `activationConstraint` у dnd-kit, чтобы меню и перетаскивание
расходились по одной границе.

Отдельный риск, который пришлось закрыть: проп `onPointerDown` на элементе
перекрывает обработчик из `listeners` dnd-kit. Обработчик вызывается вручную,
иначе перетаскивание перестало бы запускаться.

**Проверено в реальном Chrome после правки:**

| проверка | результат |
|---|---|
| десктоп: drag мышью активируется (композиция не сломала dnd-kit) | true |
| тач: меню открылось во время настоящего удержания | true |
| тач: меню осталось после отпускания пальца | true |
| тач: модалка задачи не всплыла | true |
| тач: сдвиг пальцем меню не открыл | true |

Скриншот `lp-01-hold.png` просмотрен: лоток над доской, модалки нет.
Компонентные тесты: 5 новых на таймер удержания, включая отмену по сдвигу,
отмену по раннему отпусканию и игнорирование мыши.

## 8. Тап по полю ввода приближал страницу

**Причина.** iOS Safari принудительно приближает страницу при фокусе на
контроле с `font-size` меньше 16px и обратно не отдаляет. Замер показал, что
**все** поля приложения были 13–14px: `.input` даёт `text-sm` (14px), а
QuickAdd, описание и теги навешивают сверху `text-[13px]`.

**Исправление.** Правило `@media (pointer: coarse)` поднимает
`input/textarea/select` до 16px. Ключ по типу указателя, а не по ширине
экрана: приближение зависит от устройства — iPad в альбомной ориентации шире
`sm` и всё равно приближает.

Правило намеренно вне `@layer`: утилиты Tailwind лежат в слое `utilities`, а
неслоевой CSS побеждает любой слой независимо от специфичности — иначе
понадобился бы `!important`.

Вариант с `maximum-scale=1` во viewport отвергнут: он запрещает пользователю
масштабировать страницу вообще, это нарушение WCAG 1.4.4 и прямое
противоречие уже проведённому в проекте аудиту по Web Interface Guidelines.

**Проверено замером вычисленных стилей:**

| окружение | было | стало |
|---|---|---|
| тач (`pointer: coarse`), все 10 контролов | 13–14px | 16px |
| десктоп (`pointer: fine`), поля входа | 14px | 14px — дизайн не изменился |

## 9. Что из этого следует для метода

Эмуляция мобильного вьюпорта в headless Chrome не заменяет проверку на iOS:
она не воспроизводит ни отсутствие `contextmenu`, ни авто-приближение по
`font-size`. Оба дефекта нашлись только на живом устройстве владельца.
Для жестов и поведения форм на iPhone нужна ручная проверка на устройстве.
